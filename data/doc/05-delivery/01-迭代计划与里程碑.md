# 迭代计划与里程碑

## 1. 前置假设

| 项 | 假设 |
| --- | --- |
| 团队 | 前端 2（小程序）× 后端 2 + 设计 1（兼 UI 切图/插画对接）+ 测试 1（后期介入） |
| 周期 | 单迭代 1 周，5 个工作日；每迭代末可演示 |
| 范围 | 只做用户端（普通用户），主理人/后台能力后置 |
| 依赖 | 设计稿需覆盖 13 屏 + 6 个待补页面；插画资源需提前 2 周下单 |

## 2. 里程碑

### M0 设计基线（第 1 周）

| 交付 | 说明 |
| --- | --- |
| 设计令牌 + 组件库骨架 | `variables.wxss`、base 层 7 个组件可跑通（nav-bar/privacy-modal/skeleton/empty/tag/avatar/badge；按钮/胶囊/卡片用 class） |

**出口标准**：真机打开首页能渲染 mock 数据；能完成一次微信登录。

## 3. 关键路径与依赖

```
设计令牌 → 组件库 → 首页 → 打卡列表/详情 → 报名 → 票夹
                                        ↓
                                    打卡提交 → 通关判定 → 奖牌 → 榜单
```

- **关键路径上的第一风险是设计稿到位时间**，尤其 6 个待补页面（活动详情/打卡提交/发布/榜单/影集/奖牌墙）。
- 后端接口按"首页聚合 → 报名 → 打卡"顺序交付，前端可用 mock（`msw` 或本地 JSON）并行。

## 4. 并行策略

| 并行组 | 内容 |
| --- | --- |
| A（前端 1） | 首页、活动、票夹 |
| B（前端 2） | 打卡、我的、兴趣天梯、消息 |
| C（后端 1） | 用户/活动/报名/票/上传 |
| D（后端 2） | 挑战赛/打卡/奖牌/榜单/消息 |

接口冻结后使用 `openapi-typescript` 生成类型，两个前端共享同一份 `services/types`。

## 5. 验收口径

| 维度 | 标准 |
| --- | --- |
| 功能 | 本文档《功能需求与优先级》P0 项 100% 通过 |
| 视觉 | 与设计稿像素比对，关键页面（首页/我的/详情）偏差 ≤4rpx |
| 性能 | 首页首屏 ≤1.8s（4G 中端机），主包 ≤1.5MB |
| 稳定性 | 崩溃率 <0.1%，接口成功率 >99% |
| 合规 | 首次进入必弹隐私弹窗；协议可查；注销可入口 |
| 兼容 | 基础库 ≥2.25，覆盖 iOS 15+/Android 9+ |
