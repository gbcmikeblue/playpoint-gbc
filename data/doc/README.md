## 3. 一句话结论

一个 5 Tab 的城市兴趣社交小程序（**练手项目，以同类产品截图作参考，不复刻其品牌**）：**首页发现 → 活动/挑战赛报名 →（模拟支付）→ 现场打卡 → 奖牌与个人兴趣档案（兴趣天梯/MBTI）→ 站内消息**。
技术落点：**微信原生小程序 + TypeScript（6 分包）+ NestJS + PostgreSQL + Redis + COS**；**不接微信支付**，自绘收银台跑通"下单→支付→出票"；10 周分 5 个里程碑交付。

## 4. 关于"用最少 token 识图"的方法论

### 4.1 成本公式
图像 token ≈ `宽 × 高 / 750`（视觉模型通用估算）。所以**决定成本的是分辨率，不是文件大小**（PNG 388KB 与 JPG 60KB 在 token 上等价）。

| 尺寸 | 单图 token | 用途 |
| --- | --- | --- |
| 416×781（原始） | ≈ 433 | 完整信息（文字可读） |
| 750×1400 | ≈ 1400 | 二次放大会浪费，不需要 |
| 208×390（半缩） | ≈ 108 | 只看版式色块，文字全糊 |
| 300×300 局部裁剪 | ≈ 120 | **补充细节的最优解** |

### 4.2 本项目实际采用的策略（合计 ≈ 6.9k token 覆盖 13 屏）

1. **先量尺寸再决定**：13 张里 12 张只有 416×781，本身已低于"值得压缩"的阈值（再缩就丢字），所以**直接读原图最省**——降采样反而要读两次。
2. **一次性全读，不来回**：按模块分组并行读（首页/打卡 4 张 → 我的/天梯 5 张 → 消息/资料 3 张），避免"读一张问一句"导致的上下文重复计费。
3. **只读一次，结论落盘**：所有视觉结论写入 `99-evidence/01-截图识图记录.md`，后续开发查文本，**永不重读图**。这是最大的节省项——否则每次对话都要重付 7k。
4. **按需补局部**：将来若需要确认某个按钮的确切颜色或某个被省略的文案，用 PIL 裁出该区域（如 300×300，≈120 token）单独读，成本是整图的 1/4。
5. **不做的事**：不拼图（拼接不减少总像素，反而降低单图清晰度）；不 OCR（截图文字量小，OCR 的调用成本高于直接读图）；不逐张反复确认。
